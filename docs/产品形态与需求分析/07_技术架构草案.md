# 技术架构草案

## 当前项目现实

KeeperKit 现在已经有一个可用的规则书 RAG 基础：

- FastAPI 后端
- React 前端
- 文档加载、切块、向量检索
- 规则问答接口
- 本地索引和本地资料目录

所以模组助手的架构应当建立在这个基础上，而不是推倒重来。

## 多知识库方向

未来可规划为多知识库架构：

- 规则书知识库
- 模组知识库
- 用户笔记知识库
- 跑团记录知识库
- 玩家角色卡知识库
- 图片 / 手牌资产索引

这个设计能让系统按任务类型和当前模组选择合适的数据源。

## 数据流草案

一个典型流程可以是：

用户输入问题
-> 判断任务类型
-> 选择当前模组
-> 检索模组知识库
-> 必要时检索规则书
-> 必要时检索用户笔记或记录
-> LLM 生成结构化结果
-> 返回 sources、建议和风险提示

这套流程适合问答，也适合时间线整理和改写建议。

## 本地优先与未来云端

当前 demo 阶段适合本地优先：

- 资料本地保存
- 索引本地保存
- 版本记录本地保存

未来如果要上线，再考虑：

- 云端同步
- 多设备使用
- 账号体系
- 分享和协作

## 插件化方向

KeeperKit 的架构可以保留插件化空间，例如：

- 规则系统插件
- 骰子插件
- 图片生成插件
- 导出插件
- 不同 LLM provider 插件

这样做的好处是，功能分离清楚，也更容易扩展到不同玩法。

## 架构原则

技术架构上应尽量遵守以下原则：

- CoC 优先，但不要把所有东西硬编码成 CoC 独占。
- 原始内容、AI 建议和修订内容必须分层。
- 前端要能同时承载结构化内容和来源引用。
- 组件和服务要尽量保持可替换。
